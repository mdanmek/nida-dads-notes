# แผนการปรับปรุงรอบที่ 2: จากผลวิเคราะห์สู่เรื่องเล่าสำหรับผู้อ่านครั้งแรก

## เป้าหมายของรอบนี้

ปรับการนำเสนอส่วนโครงการจ้างก่อสร้างให้ผู้อ่านที่ไม่เคยเห็นข้อมูล e-GP
เข้าใจได้ตั้งแต่บริบทของข้อมูล เหตุผลที่เลือกวิเคราะห์ คำถามที่ต้องการตอบ
หลักฐานที่พบ และข้อสรุปที่ข้อมูลรองรับ

รอบนี้เน้น **ความต่อเนื่องของเรื่องราวและความสัมพันธ์ระหว่างคำถามกับคำตอบ**
โดยใช้กระบวนการวนซ้ำดังนี้:

```text
Notebook และ Output
        ↓
Figure และตารางหลัก
        ↓
README
        ↓
Review เรื่องราวและความสอดคล้อง
        ↓
Revision plan
        ↓
ปรับ Notebook และรันใหม่
```

หลักสำคัญคือ README ต้องอ้างอิงผลที่สร้างจาก Notebook เท่านั้น
หากต้องเพิ่มหรือแก้ตัวเลข กราฟ หรือกรณีศึกษา ต้องแก้ที่ Notebook
และรันใหม่ก่อนนำผลไปแก้ README

## 1. ผลการรีวิว README ปัจจุบัน

### 1.1 สิ่งที่ทำได้ดี

- ตัวเลขสำคัญสอดคล้องกับผลลัพธ์ของ Notebook
- แยกตัวชี้วัดคุณภาพข้อมูลออกจากตัวชี้วัดด้านการจัดซื้อจัดจ้าง
- ระบุชัดว่าผลลัพธ์เป็นเครื่องมือคัดกรอง ไม่ใช่หลักฐานการทุจริต
- มีคำถาม ขอบเขต วิธีเตรียมข้อมูล EDA ตัวชี้วัด กรณีศึกษา และข้อจำกัด
- รูปที่ใช้ใน README เชื่อมโยงกับผลจาก Notebook จริง
- กรณีศึกษาช่วยให้ตัวชี้วัดที่เป็นนามธรรมเห็นภาพได้มากขึ้น
- การสรุปจาก 178,978 โครงการเหลือ 103 โครงการทำให้เห็นประโยชน์ของงาน

### 1.2 ข้อสรุปจากการรีวิว

README ปัจจุบัน **เข้าใจได้สำหรับผู้ที่คุ้นเคยกับข้อมูลหรือการวิเคราะห์**
แต่ยังไม่เพียงพอสำหรับผู้อ่านครั้งแรกที่ไม่รู้จัก e-GP เพราะลำดับปัจจุบัน
ยังคล้ายการสรุปผลตามลำดับ Notebook มากกว่าการพาผู้อ่านค้นพบคำตอบทีละขั้น

จุดที่ขาดไม่ใช่จำนวนข้อมูล แต่เป็น “สะพานเชื่อม” ระหว่างข้อค้นพบ เช่น:

1. เหตุใดงานก่อสร้างซึ่งมีเพียง 4.54% ของรายการทั้งหมดจึงถูกเลือกศึกษา
2. เหตุใดการกระจุกตัวใกล้ 500,000 บาทจึงนำไปตรวจวิธีเฉพาะเจาะจง
3. เหตุใดภาพ Pareto ของผู้รับจ้างทั้งประเทศจึงนำไปสู่การวิเคราะห์
   ความสัมพันธ์ระดับหน่วยงานย่อย–ผู้รับจ้าง
4. เหตุใดค่าผิดสังเกตของราคาจึงต้องผ่านการตรวจคุณภาพข้อมูลก่อน
5. ตัวชี้วัดแต่ละมิติตอบคำถามใด และช่วยลดขอบเขตการตรวจสอบอย่างไร

## 2. ผู้อ่านเป้าหมายและสิ่งที่ต้องเข้าใจก่อนอ่านผล

กำหนดผู้อ่านเป้าหมายเป็นผู้ที่:

- ไม่เคยเห็นข้อมูล e-GP
- ไม่รู้ความแตกต่างระหว่างรายการ โครงการ สัญญา และผู้รับจ้าง
- ไม่คุ้นเคยกับคำว่า percentile, log scale, Pareto หรือ Supplier Entity
- ยังไม่รู้ความหมายของวงเงินงบประมาณ ราคากลาง และราคาที่ตกลง
- ไม่ทราบเหตุผลที่ตัวเลขใกล้ 500,000 บาทได้รับความสนใจ

เมื่ออ่าน README จบ ผู้อ่านต้องสามารถตอบได้ว่า:

1. ข้อมูลนี้บันทึกอะไร และหนึ่งแถวหมายถึงอะไร
2. เหตุใดจำนวนแถว 180,079 จึงไม่เท่ากับจำนวนโครงการ 178,978
3. งานก่อสร้างมีรูปแบบสำคัญอะไร
4. ข้อค้นพบจาก EDA พัฒนาเป็นตัวชี้วัดอย่างไร
5. เหตุใด 103 โครงการจึงถูกจัดลำดับให้ตรวจสอบก่อน
6. เหตุใดผลลัพธ์จึงยังไม่สามารถใช้กล่าวหาการทุจริตได้

## 3. เส้นเรื่องใหม่ของ README

ใช้เส้นเรื่องหลักดังนี้:

### ช่วงที่ 1: เริ่มจากภาพใหญ่และตั้งคำถาม

- ข้อมูล e-GP คือข้อมูลโครงการจัดซื้อจัดจ้างภาครัฐ
- ข้อมูลปี 2569 มี 3,964,924 รายการจาก 8 ไฟล์
- งานก่อสร้างมี 180,079 รายการ แม้คิดเป็นเพียง 4.54% แต่มีทั้งโครงการ
  ขนาดเล็กจำนวนมากและโครงการมูลค่าสูง จึงเหมาะกับการศึกษาความแตกต่าง
  ของวิธีจัดซื้อ ราคา หน่วยงาน และผู้รับจ้าง
- ตั้งคำถามกลางว่า  
  **“ในโครงการจ้างก่อสร้างเกือบ 180,000 โครงการ มีรูปแบบใดที่ช่วย
  คัดกรองโครงการซึ่งควรเปิดเอกสารตรวจสอบก่อน?”**

> หมายเหตุ: เหตุผลด้านมูลค่าของงานก่อสร้างควรยืนยันอีกครั้งหลังเชื่อม
> Notebook ภาพรวมปี 2567–2569 ห้ามอ้างสัดส่วนมูลค่าที่ยังไม่ได้คำนวณ

### ช่วงที่ 2: อธิบายภาษาของข้อมูล

อธิบายคำสำคัญด้วยภาษาทั่วไปก่อนใช้ในการวิเคราะห์:

| คำ | ความหมายในการวิเคราะห์นี้ |
|---|---|
| รายการหรือแถว | ระเบียนหนึ่งแถวในไฟล์ ซึ่งอาจเป็นโครงการ สัญญา หรือสมาชิกกิจการร่วมค้า |
| โครงการ | หน่วยหลักที่ระบุด้วย `รหัสโครงการ` |
| สัญญา | ข้อตกลงภายใต้โครงการ โครงการหนึ่งอาจมีหลายสัญญา |
| ผู้รับจ้าง | ผู้ชนะการเสนอราคาหรือคู่สัญญา |
| วงเงินงบประมาณ | กรอบงบประมาณที่กำหนดสำหรับโครงการ |
| ราคากลาง | ราคาอ้างอิงของโครงการ |
| ราคาที่ตกลง | ยอดรวมราคาที่ตกลงของทุกสัญญาในโครงการ |
| Supplier Entity | หน่วยผู้รับจ้างที่ใช้รวมมูลค่า โดยไม่นับสมาชิกกิจการร่วมค้าซ้ำ |

ส่วนนี้ต้องทำให้ผู้อ่านเข้าใจว่า 180,079 แถวถูกปรับเป็น
178,978 โครงการก่อนเริ่ม EDA

### ช่วงที่ 3: ให้ข้อมูลพาผู้อ่านพบเบาะแส

เรียงข้อค้นพบใหม่เป็นลำดับเหตุผล:

1. **โครงการส่วนใหญ่มีขนาดเล็ก**  
   76.34% มีงบประมาณไม่เกิน 500,000 บาท

2. **พบการกระจุกตัวใกล้ 500,000 บาท**  
   ช่วง 400,000–500,000 บาทมีสัดส่วนมากที่สุด และพบค่าซ้ำจำนวนมาก
   ที่ 500,000, 499,000, 498,000 และค่าที่ใกล้เคียง

3. **ตรวจว่าวิธีจัดซื้ออธิบายรูปแบบนี้หรือไม่**  
   วิธีเฉพาะเจาะจงมี 76.35% ของจำนวนโครงการ แต่คิดเป็น 9.33%
   ของวงเงินรวม และ 99.57% ของโครงการวิธีนี้มีงบไม่เกิน 500,000 บาท

4. **ตรวจความสัมพันธ์ของราคา**  
   โครงการส่วนใหญ่มีราคาที่ตกลงไม่เกินงบประมาณหรือราคากลาง
   แต่ต้องแยกค่าผิดสังเกตของราคากลางออกก่อนสร้างตัวชี้วัด

5. **ตรวจว่าใครเป็นผู้ดำเนินโครงการ**  
   จำนวนและมูลค่ากระจายต่างกันตามหน่วยงาน ส่วนผู้รับจ้างระดับประเทศ
   ไม่ได้ถูกครองโดยรายเดียว แต่ควรตรวจต่อในระดับหน่วยงานย่อย

6. **เปลี่ยนเบาะแสเป็นตัวชี้วัดที่ตรวจสอบได้**  
   พัฒนาตัวชี้วัด 3 มิติ โดยกำหนดเงื่อนไขและฐานคำนวณให้ชัดเจน

### ช่วงที่ 4: ตอบคำถามด้วยตัวชี้วัดและกรณีศึกษา

- แสดงจำนวนโครงการของตัวชี้วัดแต่ละมิติ
- อธิบายการซ้อนทับก่อนแสดงระดับ High priority
- ใช้กรณีศึกษา 2 กรณีเพื่อแสดงว่า indicator ชี้ให้ไปตรวจอะไร
- ปิดเรื่องด้วยสิ่งที่ตอบได้ สิ่งที่ยังตอบไม่ได้ และข้อมูลที่ต้องเพิ่ม

## 7. มาตรฐาน Figure

ใช้รูปแบบชื่อไฟล์:

```text
fig<หมายเลข notebook>_<ลำดับรูปสองหลัก>_<ชื่อย่อภาษาอังกฤษ>.png
```

ตัวอย่าง:

```text
fig02_01_share_of_procurement_record.png
fig03_01_project_budget_distribution.png
fig04_01_procurement_review_indicators.png
```

หลักการ:

- รูปต้องถูกสร้างและบันทึกจาก Notebook ต้นทาง
- ใช้ `fig.savefig(..., dpi=150, bbox_inches='tight')` ก่อน `plt.show()`
- ชื่อรูปต้องตรงกับลำดับที่ปรากฏใน Notebook
- README อ้างอิงเฉพาะรูปที่มีหน้าที่ตอบคำถาม
- หากแก้กราฟ ต้องรัน Notebook และแทนที่ไฟล์รูปก่อนแก้ข้อสรุปใน README
- ใช้สี รูปแบบตัวอักษร และหน่วยให้สอดคล้องกันทุก Notebook
- ใต้รูปทุกภาพใน README ต้องมีชื่อรูปแบบเอกสารทางวิชาการ
- ใช้เลขรูปเรียงต่อเนื่องตามลำดับที่ปรากฏใน README ได้แก่
  `รูปที่ 1`, `รูปที่ 2`, `รูปที่ 3` และต่อไปจนถึงรูปสุดท้าย
- เลขรูปใน README แยกจากเลขชื่อไฟล์ เช่น
  `fig03_01_...` อาจเป็น `รูปที่ 2` หากมีรูปจาก Notebook 02 อยู่ก่อนหน้า
- ใช้รูปแบบคำบรรยายใต้ภาพว่า
  `รูปที่ <ลำดับ>: <ชื่อภาพที่อธิบายสิ่งซึ่งภาพแสดง>`
- ชื่อภาพต้องบอกสาระของรูปอย่างกระชับ และไม่ใช้เพียงชื่อไฟล์
- วางคำบรรยายไว้ใต้รูปและจัดกึ่งกลางให้สม่ำเสมอ
- ในเนื้อเรื่องให้อ้างถึงรูปด้วยเลข เช่น “จากรูปที่ 3 พบว่า...”
  แทนคำว่า “จากรูปด้านล่าง”
- หากเพิ่ม ลบ หรือย้ายรูป ต้องตรวจและรันเลขรูปใหม่ตั้งแต่ต้น README
- Caption ใน README ต้องอธิบาย “สิ่งที่ควรเห็น” ไม่ใช่ทวนชื่อกราฟ
- รูปที่ไม่ได้ช่วยขับเรื่องให้อยู่ใน Notebook แต่ไม่จำเป็นต้องใส่ README

ตัวอย่างการเขียนใน README:

```html
<p align="center">
  <img src="figure/fig03_01_project_budget_distribution.png"
       alt="การกระจายวงเงินงบประมาณของโครงการจ้างก่อสร้าง">
</p>
<p align="center">
  <em>รูปที่ 2: การกระจายวงเงินงบประมาณของโครงการจ้างก่อสร้างในสเกลปกติและสเกลลอการิทึม</em>
</p>
```

ข้อความก่อนรูปต้องบอกว่ากำลังตรวจคำถามใด ส่วนข้อความหลังรูปต้องอธิบาย
ข้อค้นพบและเชื่อมไปยังคำถามถัดไป โดยไม่ปล่อยให้รูปทำหน้าที่เล่าเรื่องเพียงลำพัง
