## 1. เป้าหมายของการปรับรอบนี้

ปรับ Notebook และ README ให้ตอบคำถามของโครงการอย่างเป็นลำดับว่า:

> **ภายใต้โครงการจ้างก่อสร้างที่ใช้วิธีเฉพาะเจาะจงและมีวงเงินไม่เกิน 500,000 บาท มีรูปแบบผิดสังเกตใดเกิดขึ้นซ้ำ และรูปแบบเหล่านั้นเชื่อมโยงกับหน่วยงาน ผู้รับจ้าง พื้นที่ เวลา และราคาอย่างไร?**

เส้นเรื่องหลักต้องเป็น:

```text
งานจัดซื้อจัดจ้างทั้งหมด
→ งานจ้างก่อสร้าง
→ พบการกระจุกใกล้ 500,000 บาท
→ กฎหมายอธิบายเหตุผลเชิงโครงสร้างของการกระจุก
→ แยกสิ่งที่กฎหมายอธิบายได้ออกจากสิ่งที่กฎหมายอธิบายไม่ได้เพียงลำพัง
→ ตรวจหารูปแบบผิดสังเกตที่เกิดซ้ำ
→ วิเคราะห์การซ้อนทับ
→ จัดลำดับกรณีสำหรับตรวจเอกสารต่อ
```

เป้าหมายไม่ใช่การพิสูจน์การทุจริต การแบ่งซื้อแบ่งจ้าง การฮั้ว หรืออิทธิพลทางการเมือง แต่เป็นการใช้ EDA สร้างคำถามและลดขอบเขตของโครงการที่ควรตรวจสอบเพิ่มเติม

ข้อมูลทุกส่วนต้องระบุว่าเป็น **ข้อมูลปีงบประมาณ 2569 สะสมถึงวันที่ 30 กรกฎาคม 2569 ไม่ใช่ข้อมูลเต็มปี**

## 2. สิ่งที่เปลี่ยนจาก revise05

`revise05.md` เน้นการอธิบายที่มาของ threshold และการสร้างตัวชี้วัด รอบนี้ให้คงส่วนดังกล่าวไว้ แต่เปลี่ยนกรอบการเล่าจาก “ตัวชี้วัด 3 ตัว” เป็น “การค้นหา anomaly pattern หลังควบคุมบริบทกฎหมาย”

สิ่งที่ต้องเปลี่ยน:

- ใช้คำว่า **รูปแบบผิดสังเกต** หรือ **รูปแบบที่ควรตรวจต่อ** แทนการนำเสนอ flag แบบแยกส่วน
- ยืนยันว่าเพดาน 500,000 บาทและการใช้วิธีเฉพาะเจาะจงเป็นรูปแบบที่กฎหมายอธิบายได้ ไม่ใช่ anomaly ด้วยตัวเอง
- แยก anomaly เป็น 4 ระดับ: Project, Group, Relationship และ Network
- จัด 3 รูปแบบเดิมเป็น Pattern หลัก ได้แก่ ราคา/สัญญา การเกิดซ้ำใกล้เพดาน และการพึ่งพาผู้รับจ้างภายในหน่วยงาน
- เพิ่มการสำรวจ **Geographic supplier dominance** ระดับจังหวัดเป็น Pattern เชิงพื้นที่
- ยังไม่รวม Pattern เชิงพื้นที่เข้ากับคะแนนซ้อนทับเดิม จนกว่าจะตรวจ sensitivity และคุณภาพข้อมูลพื้นที่แล้ว
- เก็บ Cross-agency, temporal burst, repeated amount และ text similarity เป็น Future Work เว้นแต่การรัน Pattern หลักเสร็จและมีเวลาเพียงพอ
- Markdown ต้องตั้งคำถามก่อน Code แสดงผลจาก Output แล้วจึงตีความ ห้ามบรรยายผลล่วงหน้า

## 4. หลักการแยกสิ่งที่กฎหมายอธิบายได้

### 4.1 Expected structural pattern

สิ่งต่อไปนี้มีคำอธิบายจากกฎหมายและไม่ถือเป็น anomaly โดยลำพัง:

- โครงการวิธีเฉพาะเจาะจงจำนวนมากมีวงเงินไม่เกิน 500,000 บาท
- ค่า 500,000 บาทปรากฏบ่อยกว่าค่าบริเวณอื่น
- จำนวนโครงการกระจุกตัวใต้เส้นแบ่งดังกล่าว

### 4.2 Residual anomaly

หลังควบคุมวิธีจัดซื้อและวงเงินแล้ว ให้ถามต่อว่า:

- เหตุใดหน่วยงานเดียว ผู้รับจ้างเดียว และวันเดียวกันจึงมีหลายโครงการใกล้เพดานพร้อมกัน
- เหตุใดผู้รับจ้างรายเดียวจึงได้รับทั้งจำนวนและมูลค่างานส่วนใหญ่ของบางหน่วยงานหรือบางจังหวัด
- เหตุใดราคาที่ตกลงรวมจึงสูงกว่างบประมาณหรือราคากลางในระดับที่มีนัยเชิงปฏิบัติ
- เหตุใดบางโครงการจึงมีหลายสัญญาหรือยอดรวมระดับสัญญาไม่สอดคล้องกับระดับโครงการ

คำตอบจากข้อมูลยังเป็นเพียง **สัญญาณสำหรับตรวจเอกสารต่อ** ไม่ใช่ข้อสรุปความผิด

## 8. แผนแก้ Notebook 04 — Anomaly Pattern Detection

ไฟล์: `04_construction_review_indicators_2569.ipynb`

### 8.1 เปลี่ยนกรอบการนำเสนอ

คงคอลัมน์ `flag_*` ในโค้ดได้เพื่อความสะดวก แต่หัวข้อและคำอธิบายสำหรับผู้อ่านให้ใช้คำว่า:

- Pattern
- รูปแบบผิดสังเกต
- สัญญาณสำหรับทบทวน
- กลุ่มตรวจสอบลำดับแรก

ไม่ใช้คำว่า “พบการทุจริต”, “ผู้มีอิทธิพล”, “ฮั้ว” หรือ “แบ่งซื้อแบ่งจ้าง” เป็นข้อสรุปจากข้อมูลชุดนี้

### 8.2 ลำดับ Pattern

#### Pattern A — Material price/contract anomaly

คำถาม: มีโครงการใดที่ราคาที่ตกลงรวมสูงกว่างบประมาณหรือราคากลางในระดับที่ควรตรวจเอกสารต่อหรือไม่?

- คง sensitivity ของจำนวนเงิน 5,000 / 10,000 / 25,000 / 50,000 บาท
- คง sensitivity ของสัดส่วน 0.5% / 1% / 5%
- เกณฑ์หลักปัจจุบันคือมากกว่า 10,000 บาทและมากกว่า 1%
- แสดงผลแยกระหว่างสูงกว่างบประมาณ สูงกว่าราคากลาง และสูงกว่าทั้งสองค่า
- ตรวจจำนวนสัญญาและยอดรวมระดับสัญญาประกอบ

#### Pattern B — Near-threshold repeated pattern

คำถาม: มีหลายโครงการใกล้เพดานเกิดกับหน่วยงานย่อย ผู้รับจ้าง และวันเดียวกันหรือไม่?

- เปรียบเทียบหน้าต่าง 450–500k, 480–500k, 490–500k, 495–500k และเท่ากับ 500k
- ทดลองจำนวนขั้นต่ำ 2 / 3 / 5 / 10 โครงการต่อกลุ่ม
- เกณฑ์หลักปัจจุบันคือ 490,000–500,000 บาทและอย่างน้อย 3 โครงการ
- รายงานทั้งจำนวน cluster และจำนวนโครงการ ไม่รายงานเพียงจำนวนใดจำนวนหนึ่ง

#### Pattern C — Agency–supplier dominance

คำถาม: หน่วยงานย่อยใดพึ่งพาผู้รับจ้างรายเดียวสูงทั้งจำนวนและมูลค่า?

- ทดลองฐานขั้นต่ำ 5 / 10 / 20 โครงการ
- ทดลองส่วนแบ่ง 50% / 75% / 90%
- เกณฑ์หลักปัจจุบันคือผู้รับจ้างอย่างน้อย 10 โครงการ และอย่างน้อย 75% ทั้งจำนวนและมูลค่า
- ใช้คำว่า “การพึ่งพาผู้รับจ้างสูง” ไม่ใช้ “ตลาดกระจุกตัว” เพราะไม่มีข้อมูลผู้เสนอราคาทั้งหมด

#### Pattern D — Geographic supplier dominance (เพิ่มใหม่)

คำถาม: ภายในจังหวัด มีผู้รับจ้างรายใดครองทั้งจำนวนและมูลค่าโครงการสูงผิดจากพื้นที่อื่นหรือไม่?

หน่วยวิเคราะห์คือ `จังหวัด–ผู้รับจ้าง` ภายในกลุ่มศึกษาหลัก โดยคำนวณ:

$$
\mathrm{Project\ Share}_{s,p}
=\frac{\mathrm{Projects\ won\ by\ supplier}\ s\ \mathrm{in\ province}\ p}
{\mathrm{All\ projects\ in\ province}\ p}
$$

$$
\mathrm{Value\ Share}_{s,p}
=\frac{\mathrm{Awarded\ value\ of\ supplier}\ s\ \mathrm{in\ province}\ p}
{\mathrm{All\ awarded\ value\ in\ province}\ p}
$$

ขั้นตอน:

1. ใช้หนึ่งแถวต่อ `project_id–supplier` หลังจัดการข้อมูลซ้ำและ JV
2. ตัดแถวที่จังหวัดหรือผู้รับจ้างใช้วิเคราะห์ไม่ได้ พร้อมรายงานจำนวนที่ถูกตัด
3. คำนวณยอดรวมโครงการและมูลค่าของแต่ละจังหวัด
4. คำนวณจำนวนโครงการและมูลค่าของแต่ละคู่จังหวัด–ผู้รับจ้าง
5. ทดลองเกณฑ์พื้นที่อย่างน้อย 20 โครงการ ผู้รับจ้างอย่างน้อย 10 โครงการ และส่วนแบ่ง 50% / 75% / 90% ทั้งสองมิติ
6. แสดง sensitivity ก่อนเลือกเกณฑ์หลัก ห้ามเลือกค่าเพียงเพราะให้จำนวนกรณีที่ต้องการ
7. เปรียบเทียบการกระจาย top-supplier share ระหว่างจังหวัด เพื่อให้เห็นว่ากรณีใดต่างจากพื้นที่ทั่วไป
8. ถ้ามี mapping ภูมิภาคที่ตรวจสอบได้ จึงสรุปภาพรวมระดับภูมิภาคเป็นบริบทเสริม ไม่ใช้ภูมิภาคแทนจังหวัดในการตรวจ Pattern หลัก

ข้อจำกัดที่ต้องเขียนคู่กับผล:

- การครองงานสูงอาจเกิดจากความเชี่ยวชาญ ระยะทาง ต้นทุนขนส่ง หรือผู้ประกอบการในพื้นที่มีน้อย
- จังหวัดไม่ใช่นิยามตลาด และข้อมูลไม่มีผู้เสนอราคาทั้งหมด
- จึงไม่เรียกผลว่าอำนาจตลาดหรือผู้มีอิทธิพล
- Pattern นี้ใช้ชี้คู่จังหวัด–ผู้รับจ้างที่ควรตรวจการแข่งขันและเอกสารเพิ่มเติม

### 8.3 Overlap และ Review Priority

รอบแรกให้คำนวณ overlap จาก Pattern A–C เหมือน baseline เดิม เพื่อให้เปรียบเทียบได้

Pattern D ให้รายงานแยกเป็น exploratory result พร้อมแสดงว่าโครงการของ Pattern D ซ้อนกับ Pattern A–C เท่าใด แต่ยังไม่เพิ่มลงใน `indicator_count` หลัก

หากภายหลังตัดสินใจรับ Pattern D เป็นเกณฑ์หลัก ต้อง:

- เปลี่ยนชื่อ `indicator_count` เป็น `pattern_count`
- คำนวณ 0/1/2/3/4 Pattern ใหม่ทั้งชุด
- สร้าง pairwise overlap ใหม่
- อธิบายว่า baseline รุ่นเดิมและรุ่นใหม่เปรียบเทียบกันอย่างไร
- กำหนด Review Priority ใหม่ก่อนแก้ README

### 8.4 กรณีศึกษา

เลือกกรณีศึกษาตาม “ชนิดของคำถาม” ไม่เลือกเฉพาะค่าที่สูงที่สุด:

- กรณีราคา/หลายสัญญา 1 กรณี
- กลุ่มใกล้เพดานเกิดซ้ำ 1 กรณี
- คู่หน่วยงาน–ผู้รับจ้างที่พึ่งพาสูง 1 กรณี
- คู่จังหวัด–ผู้รับจ้างที่เด่นจาก sensitivity 1 กรณี ถ้าผลมีความหมาย
- กรณีที่พบอย่างน้อย 2 Pattern เดิม 1 กรณี

ทุกกรณีต้องมีคำถามสำหรับเปิดเอกสารต่อ เช่น TOR/BOQ สถานที่ก่อสร้าง แหล่งงบ ผู้เสนอราคา สัญญาแก้ไข และความต่อเนื่องของงาน

## 14. ข้อสรุปที่ Project ควรสามารถตอบได้

เมื่อทำตามแผนนี้ Project ต้องสรุปได้ 4 ชั้น:

1. **โครงสร้างข้อมูล:** งานก่อสร้างมีจำนวนมากและส่วนใหญ่เป็นโครงการขนาดเล็ก
2. **บริบทกฎหมาย:** การกระจุกที่ไม่เกิน 500,000 บาทสอดคล้องกับเงื่อนไขวิธีเฉพาะเจาะจง จึงไม่ผิดสังเกตด้วยตัวเอง
3. **Residual patterns:** ภายในกลุ่มที่อยู่ใต้เงื่อนไขเดียวกัน ยังพบรูปแบบเกิดซ้ำ ความสัมพันธ์ผู้รับจ้าง การกระจุกเชิงพื้นที่ และความไม่สอดคล้องด้านราคาที่กฎหมายไม่สามารถอธิบายได้เพียงลำพัง
4. **การใช้ผล:** การซ้อนทับของหลาย Pattern ช่วยจัดลำดับโครงการหรือความสัมพันธ์ที่ควรเปิดเอกสารตรวจสอบก่อน โดยไม่ใช้ผล EDA เป็นคำตัดสินความผิด

> **เพดาน 500,000 บาทอธิบายได้ว่าทำไมโครงการวิธีเฉพาะเจาะจงจึงกระจุกตัว แต่ไม่ได้อธิบายว่าทำไมบางหน่วยงาน ผู้รับจ้าง พื้นที่ และช่วงเวลาจึงเกิดรูปแบบเดิมซ้ำหรือซ้อนทับกัน การวิเคราะห์จึงมุ่งค้นหา Pattern เหล่านี้เพื่อจัดลำดับการตรวจสอบ ไม่ใช่เพื่อตัดสินการทุจริตจากข้อมูลเพียงชุดเดียว**
