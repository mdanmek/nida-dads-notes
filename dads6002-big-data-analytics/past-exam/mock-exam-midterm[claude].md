## ข้อ 1 (10 คะแนน)

**โจทย์** จงอธิบายวิธีที่ HDFS เก็บไฟล์ขนาด 300 MB ที่ตั้งค่า block size 128 MB และ replication factor 3 ว่าได้กี่ block ใช้พื้นที่จริงเท่าไร และอธิบายขั้นตอนที่ client อ่านไฟล์นี้ พร้อมบอกว่าทำไม HDFS จึงเหมาะกับไฟล์ขนาดใหญ่จำนวนไม่มาก

**แนวคำตอบ**

HDFS ตัดไฟล์เป็น block ขนาดเท่ากันตาม block size ไฟล์ 300 MB กับ block size 128 MB จึงได้ 3 block คือ block ที่ 1 ขนาด 128 MB block ที่ 2 ขนาด 128 MB และ block ที่ 3 ขนาด 44 MB block สุดท้ายใช้พื้นที่เท่าข้อมูลจริงคือ 44 MB ไม่ได้จองเต็ม 128 MB เมื่อ replication factor เท่ากับ 3 แต่ละ block มีสำเนา 3 ชุดวางไว้ต่าง DataNode จึงมี block รวม 9 ชุด และใช้พื้นที่ดิสก์ทั้ง cluster ประมาณ 900 MB การกระจายสำเนาไว้ต่างเครื่องทำให้ถ้า DataNode หนึ่งเครื่องเสีย ข้อมูลยังอ่านได้จากสำเนาอื่น และ NameNode จะสั่งทำสำเนาเพิ่มให้ครบ 3 ชุด

ขั้นตอนการอ่าน client ส่งคำขอไปที่ NameNode ว่าต้องการอ่านไฟล์นี้ NameNode ตอบกลับเป็นรายการ block ทั้ง 3 block และตำแหน่ง DataNode ที่เก็บสำเนาของแต่ละ block จากนั้น client ติดต่อ DataNode ที่อยู่ใกล้ที่สุดเพื่ออ่าน block ที่ 1, 2 และ 3 ตามลำดับโดยตรง ข้อมูลจริงไม่ได้ผ่าน NameNode ถ้า DataNode ตัวใดอ่านไม่ได้ client จะไปอ่านจากสำเนาบน DataNode ตัวอื่น

HDFS เหมาะกับไฟล์ใหญ่จำนวนไม่มากเพราะ NameNode เก็บ metadata ของทุกไฟล์และทุก block ไว้ในหน่วยความจำ ไฟล์เล็กจำนวนมากทำให้ metadata มากจนหน่วยความจำของ NameNode เต็มก่อนดิสก์ของ cluster จะเต็ม นอกจากนี้ HDFS ออกแบบให้อ่านข้อมูลต่อเนื่องเป็นก้อนใหญ่ (high throughput) และทำงานแบบ WORM คือเขียนครั้งเดียวอ่านหลายครั้ง แก้กลางไฟล์ไม่ได้ จึงเหมาะกับไฟล์ข้อมูลดิบขนาดใหญ่ที่นำมาวิเคราะห์ซ้ำหลายรอบ

## ข้อ 2 (15 คะแนน)

**โจทย์** จงอธิบาย Lambda Architecture ว่าประกอบด้วยชั้นใดบ้าง แต่ละชั้นทำหน้าที่อะไร มีข้อดีข้อเสียอย่างไร และอธิบายความแตกต่างระหว่าง Data Lake กับ Data Warehouse

**แนวคำตอบ**

Lambda Architecture เป็นสถาปัตยกรรมประมวลผล Big Data ที่ต้องการทั้งความถูกต้องของผลจากข้อมูลทั้งหมด และความเร็วของผลจากข้อมูลล่าสุด จึงแยกการประมวลผลเป็นสามชั้น

ชั้นแรกคือ batch layer เก็บข้อมูลดิบทั้งหมดไว้เป็น master dataset ที่ไม่แก้ไข (immutable) มีแต่เพิ่มข้อมูลใหม่ต่อท้าย แล้วคำนวณผลจากข้อมูลทั้งหมดใหม่เป็นรอบ ๆ เช่นทุกคืน ผลที่ได้ถูกต้องครบถ้วน แต่ช้า เพราะต้องประมวลผลข้อมูลปริมาณมาก เครื่องมือที่ใช้เช่น HDFS กับ MapReduce หรือ Hive

ชั้นที่สองคือ speed layer ประมวลผลเฉพาะข้อมูลที่เข้ามาหลังจาก batch รอบล่าสุด ให้ผลเร็วแบบเกือบ real-time เพื่อปิดช่องว่างระหว่างรอบ batch ผลจากชั้นนี้อาจไม่ละเอียดเท่า และจะถูกแทนที่เมื่อ batch รอบถัดไปคำนวณเสร็จ

ชั้นที่สามคือ serving layer รวมผลจาก batch layer กับ speed layer เข้าด้วยกัน แล้วให้ผู้ใช้หรือแอปพลิเคชัน query ได้ ตัวอย่างเช่นยอดคงเหลือยาในคลัง batch layer คำนวณยอดถึงเที่ยงคืนเมื่อวาน speed layer คำนวณยอดเบิกตั้งแต่เที่ยงคืนจนถึงตอนนี้ serving layer นำมารวมเป็นยอดคงเหลือปัจจุบัน

ข้อดีของ Lambda คือได้ทั้งผลที่ถูกต้องและผลที่เร็ว และทนต่อความผิดพลาด เพราะถ้าตรรกะผิดก็คำนวณใหม่จากข้อมูลดิบที่เก็บไว้ได้ ข้อเสียคือต้องเขียนและดูแลตรรกะการคำนวณสองชุด ชุดหนึ่งใน batch อีกชุดใน speed และต้องทำให้ผลทั้งสองชุดตรงกัน ระบบจึงซับซ้อน

Data Lake คือที่เก็บข้อมูลดิบทุกรูปแบบทั้งมีโครงสร้าง กึ่งมีโครงสร้าง และไม่มีโครงสร้าง ไว้ในรูปเดิม ใช้แนวคิด ELT (Extract, Load, Transform) คือนำเข้าข้อมูลก่อนแล้วค่อยแปลงตอนใช้ และใช้ schema on read คือกำหนดโครงสร้างตอนอ่าน จึงรับข้อมูลใหม่ได้ง่ายและยืดหยุ่น เหมาะกับงานสำรวจข้อมูลและ data science ส่วน Data Warehouse เก็บข้อมูลที่แปลงและทำความสะอาดแล้วในโครงสร้างตารางที่กำหนดไว้ล่วงหน้า ใช้แนวคิด ETL (Extract, Transform, Load) คือแปลงข้อมูลก่อนโหลด และใช้ schema on write คือข้อมูลต้องตรงกับโครงสร้างตอนเขียน ข้อมูลจึงมีคุณภาพสม่ำเสมอ เหมาะกับรายงานและ BI ในทางปฏิบัติสองแบบนี้ใช้ร่วมกัน คือข้อมูลดิบเข้า data lake ก่อน แล้วแปลงต่อเป็น data warehouse หรือ data mart สำหรับแต่ละฝ่าย

## ข้อ 3 (10 คะแนน)

**โจทย์** จงเขียน MapReduce หาอุณหภูมิเฉลี่ยของแต่ละเมืองจากไฟล์ที่แต่ละบรรทัดมีรูปแบบ `เมือง,อุณหภูมิ` และอธิบายว่าถ้าจะใช้ combiner ต้องเขียนอย่างไรจึงได้ค่าเฉลี่ยที่ถูกต้อง พร้อมอธิบายหน้าที่ของ partitioner

**แนวคำตอบ**

mapper อ่านทีละบรรทัด แยกเมืองกับอุณหภูมิ แล้วส่งเมืองเป็น key และอุณหภูมิเป็น value reducer รับเมืองหนึ่งเมืองพร้อมรายการอุณหภูมิทั้งหมด แล้วหารผลรวมด้วยจำนวน

```
map(line):
    city, temp = line.split(',')
    emit(city, (float(temp), 1))

combine(city, values):
    s = sum(v[0] for v in values)
    c = sum(v[1] for v in values)
    emit(city, (s, c))

reduce(city, values):
    s = sum(v[0] for v in values)
    c = sum(v[1] for v in values)
    emit(city, s / c)
```

ตัวอย่างข้อมูล BKK,30 BKK,32 CNX,25 BKK,34 ได้ผล BKK เท่ากับ (30+32+34)/3 = 32 และ CNX เท่ากับ 25

combiner คือ reducer ย่อยที่รันบนเครื่อง mapper เพื่อรวมผลบางส่วนก่อนส่งข้ามเครือข่าย ใช้ได้กับการรวมที่สลับลำดับและจัดกลุ่มได้ (commutative และ associative) เช่น การบวก แต่ค่าเฉลี่ยไม่มีคุณสมบัตินี้ ถ้า combiner ส่งค่าเฉลี่ยย่อยออกไป reducer จะเฉลี่ยของค่าเฉลี่ยซึ่งผิด เช่น mapper ตัวแรกมี BKK 30, 32 เฉลี่ยได้ 31 mapper ตัวที่สองมี BKK 34 เฉลี่ย 34 ของเฉลี่ยคือ 32.5 แต่ค่าจริงคือ 32 วิธีที่ถูกคือให้ combiner ส่งคู่ (ผลรวม, จำนวน) ตามโค้ดข้างบน แล้วให้ reducer รวมผลรวมและจำนวนทั้งหมดก่อนหารครั้งเดียว ได้ (62+34)/(2+1) = 32

partitioner ทำหน้าที่ตัดสินว่าคู่ key value แต่ละคู่จะไป reducer ตัวใด ค่าเริ่มต้นคือ hash(key) mod จำนวน reducer จึงรับประกันว่า key เดียวกันไป reducer ตัวเดียวกันเสมอ วิธีนี้กระจายจำนวน key ให้ reducer เท่า ๆ กัน แต่ถ้าบาง key มีข้อมูลมากผิดปกติ (data skew) reducer ตัวนั้นจะทำงานนานกว่าตัวอื่น แก้ได้ด้วยการเขียน custom partitioner

## ข้อ 4 (15 คะแนน)

**โจทย์** จงอธิบายการจัดเก็บข้อมูลของ Hive ในระดับ table, partition และ bucket อธิบายความแตกต่างระหว่าง managed table กับ external table และอธิบายบทบาทของ Metastore กับแนวคิด schema on read

**แนวคำตอบ**

Hive จัดเก็บข้อมูลเป็นไฟล์ใน HDFS โดยใช้โครงสร้างโฟลเดอร์แทนโครงสร้างตาราง ระดับแรกคือ table ซึ่งเท่ากับหนึ่งโฟลเดอร์ใน HDFS ไฟล์ทุกไฟล์ในโฟลเดอร์นั้นคือข้อมูลของตาราง

ระดับที่สองคือ partition ซึ่งเป็นโฟลเดอร์ย่อยในโฟลเดอร์ของตาราง ตั้งชื่อในรูป คอลัมน์=ค่า และซ้อนกันตามลำดับที่ระบุใน PARTITIONED BY เช่นตาราง Sales ที่ partition ด้วย country, year, month จะมีโฟลเดอร์ Sales/country=US/year=2012/month=12 เมื่อ query มีเงื่อนไข where country='US' and year=2012 Hive อ่านเฉพาะโฟลเดอร์ที่ตรงเงื่อนไข ไม่ต้องอ่านทั้งตาราง query จึงเร็วขึ้นมาก คอลัมน์ที่ใช้ partition ควรมีจำนวนค่าไม่มาก เพราะทุกค่าสร้างโฟลเดอร์ใหม่

ระดับที่สามคือ bucket ซึ่งเป็นไฟล์หนึ่งไฟล์ในโฟลเดอร์ partition กำหนดด้วย CLUSTERED BY (คอลัมน์) INTO n BUCKETS Hive คำนวณ hash ของคอลัมน์นั้น mod จำนวน bucket เพื่อหาว่าแถวไปอยู่ไฟล์ใด เช่น CLUSTERED BY (customer_id) INTO 4 BUCKETS แถวที่มี customer_id เดียวกันจะอยู่ในไฟล์เดียวกันเสมอ ช่วยให้สุ่มตัวอย่างและ join ด้วยคอลัมน์นั้นได้เร็ว และถ้าใส่ SORTED BY ข้อมูลใน bucket จะเรียงลำดับ ทำให้ค้นด้วย binary search ได้

managed table คือตารางที่ Hive เป็นเจ้าของข้อมูล เมื่อโหลดข้อมูล Hive ย้ายไฟล์เข้าไปใน warehouse directory ของตัวเอง และเมื่อสั่ง drop table Hive ลบทั้ง metadata และไฟล์ข้อมูล external table สร้างด้วย CREATE EXTERNAL TABLE และใช้ LOCATION ชี้ไปที่ข้อมูลที่มีอยู่เดิมใน HDFS Hive ไม่ย้ายไฟล์ และเมื่อ drop table จะลบเฉพาะ metadata ไฟล์ยังอยู่ external table จึงเหมาะกับข้อมูลที่โปรแกรมอื่นใช้ร่วมด้วย เช่น ไฟล์ log ที่ Flume เขียนลง HDFS

Metastore เก็บ metadata ของ Hive คือรายชื่อ database และตาราง คอลัมน์และชนิดข้อมูล ตำแหน่งโฟลเดอร์ใน HDFS รายการ partition และการตั้งค่า bucket โดยเก็บในฐานข้อมูลเชิงสัมพันธ์แยกต่างหาก เช่น MySQL ไม่เก็บใน HDFS เพราะ metadata เป็นข้อมูลชิ้นเล็กที่ถูกอ่านและแก้บ่อย ซึ่ง HDFS ที่แก้ไฟล์ไม่ได้ทำได้ไม่ดี ข้อมูลจริงอยู่ใน HDFS ส่วนคำอธิบายข้อมูลอยู่ใน Metastore

schema on read หมายถึง Hive ไม่ตรวจข้อมูลตอนโหลด คำสั่ง LOAD DATA แค่ย้ายหรือคัดลอกไฟล์เข้าโฟลเดอร์ของตาราง Hive จะใช้ schema แปลงไฟล์เป็นแถวตอน query ผ่าน SerDe ค่าที่ไม่ตรงกับชนิดข้อมูลจะได้ NULL ข้อดีคือโหลดเร็วมากและรับข้อมูลได้ทุกรูปแบบ ข้อเสียคือข้อมูลผิดรูปแบบจะไม่ถูกตรวจพบจนกว่าจะ query

## ข้อ 5 (10 คะแนน)

**โจทย์** จงอธิบายโครงสร้างข้อมูล (data model) ของ HBase และอธิบายหลักการออกแบบ row key รวมถึงปัญหา hotspot

**แนวคำตอบ**

HBase เก็บข้อมูลเป็นตาราง (table) ที่ประกอบด้วยแถว แต่ละแถวระบุด้วย row key ซึ่งเป็น byte array และเป็น index เดียวของตาราง แถวทั้งหมดเรียงตาม row key แบบ lexicographical (เรียงตามลำดับ byte) เสมอ คอลัมน์ถูกจัดกลุ่มเป็น column family ซึ่งต้องประกาศตอนสร้างตาราง ข้อมูลของ column family เดียวกันเก็บอยู่ด้วยกันในไฟล์ชุดเดียวกัน ภายใน column family เพิ่ม column qualifier ได้อิสระทีละแถวโดยไม่ต้องประกาศล่วงหน้า แถวต่างกันจึงมีคอลัมน์ต่างกันได้ และคอลัมน์ที่ไม่มีค่าไม่ใช้พื้นที่ ค่าหนึ่งค่าเรียกว่า cell ระบุด้วย row key, column family, column qualifier และ timestamp แต่ละ cell เก็บได้หลาย version ตาม timestamp การอ่านปกติจะได้ version ล่าสุด ตัวอย่างเช่น row key DEV-0098 column reading:temperature มีค่า 37.2 ที่ timestamp หนึ่ง และ 36.8 ที่ timestamp ก่อนหน้า

เพราะ row key เป็นทางเข้าถึงข้อมูลทางเดียว ต้องออกแบบ row key ตามคำถามที่จะใช้ query ข้อมูลที่ต้องอ่านด้วยกันควรมี row key ขึ้นต้นเหมือนกัน เพื่อให้อยู่ติดกันและ scan เป็นช่วงได้ด้วย STARTROW (รวม) และ STOPROW (ไม่รวม) เช่นเก็บเว็บไซต์ด้วยโดเมนกลับด้าน org.hive.www ทำให้หน้าเว็บของโดเมนเดียวกันอยู่ติดกัน ต้องระวังการเรียงแบบ byte ด้วย ตัวเลข 1 ถึง 100 ที่เก็บเป็นข้อความจะเรียงเป็น 1, 10, 100, 11 จึงควรเติมศูนย์ข้างหน้าให้ยาวเท่ากัน เช่น 001, 010, 100

hotspot เกิดเมื่อการอ่านเขียนส่วนใหญ่ไปตกที่ Region เดียว ตัวอย่างคือใช้ timestamp เป็น row key ข้อมูลใหม่ทุกแถวมี key มากกว่าแถวเดิม จึงถูกเขียนต่อท้ายที่ Region สุดท้าย RegionServer ตัวเดียวรับงานทั้งหมดขณะที่ตัวอื่นว่าง แก้ได้ด้วยการใส่ค่าที่กระจาย เช่น hash หรือรหัสอุปกรณ์ไว้หน้า key (salting) ข้อแลกเปลี่ยนคือ scan ตามช่วงเวลาทำได้ยากขึ้น เพราะข้อมูลช่วงเวลาเดียวกันกระจายอยู่หลาย Region

## ข้อ 6 (15 คะแนน)

**โจทย์** จงอธิบายส่วนประกอบของ Kafka ได้แก่ producer, consumer, broker, topic, partition, offset และ consumer group และเปรียบเทียบการใช้งาน Kafka กับ Flume

**แนวคำตอบ**

Kafka เป็นแพลตฟอร์มสตรีมข้อมูลแบบกระจาย ใช้รับส่งข้อความ (message หรือ event) ปริมาณมากจากผู้ส่งหลายรายไปยังผู้รับหลายราย และเก็บข้อความไว้บนดิสก์ตามระยะเวลาที่กำหนด

producer คือโปรแกรมที่ส่งข้อความเข้า Kafka โดยระบุ topic ที่จะส่ง และเลือก partition ที่จะเขียน ถ้าข้อความมี key producer ใช้ hash ของ key เลือก partition ข้อความที่ key เดียวกันจึงไปอยู่ partition เดียวกันเสมอ consumer คือโปรแกรมที่อ่านข้อความจาก topic ที่สมัครไว้ broker คือเซิร์ฟเวอร์ Kafka หนึ่งเครื่อง หลาย broker รวมกันเป็น cluster ทำหน้าที่เก็บข้อความและให้บริการ producer กับ consumer

topic คือหมวดของข้อความ เช่น topic ชื่อ vital-signs สำหรับค่าสัญญาณชีพ แต่ละ topic แบ่งเป็นหลาย partition ซึ่งกระจายอยู่บนหลาย broker ทำให้เขียนและอ่านแบบขนานได้ partition แต่ละตัวเป็น log ที่เรียงลำดับและเขียนต่อท้ายอย่างเดียว Kafka รับประกันลำดับของข้อความภายใน partition เดียวเท่านั้น ไม่รับประกันข้าม partition partition ทำสำเนา (replication) ไว้บน broker อื่นเพื่อทนต่อ broker เสีย

offset คือหมายเลขลำดับของข้อความในแต่ละ partition เริ่มจาก 0 และเพิ่มทีละหนึ่ง consumer จำ offset ที่อ่านถึงแล้ว จึงอ่านต่อจากจุดเดิมได้หลังรีสตาร์ต หรือย้อนกลับไปอ่านใหม่ได้ เพราะ Kafka ไม่ลบข้อความทันทีหลังถูกอ่าน

consumer group คือกลุ่มของ consumer ที่ช่วยกันอ่าน topic เดียวกัน partition หนึ่งตัวถูกอ่านโดย consumer เพียงตัวเดียวในกลุ่ม เช่น topic มี 4 partition และกลุ่มมี consumer 2 ตัว แต่ละตัวอ่าน 2 partition ถ้ากลุ่มมี consumer 5 ตัว จะมี 1 ตัวว่างไม่ได้อ่าน จำนวน partition จึงเป็นขีดจำกัดของการอ่านแบบขนานในกลุ่มเดียว ส่วน consumer คนละกลุ่มอ่านข้อความชุดเดียวกันได้ทั้งหมดโดยไม่แย่งกัน เช่น กลุ่มหนึ่งเขียนลง HDFS อีกกลุ่มส่งการแจ้งเตือน

เมื่อเปรียบเทียบกับ Flume ทั้งสองรับข้อมูลสตรีมได้ Flume ออกแบบมาเพื่อรวบรวม log แล้วส่งเข้า Hadoop โดยเฉพาะ ตั้งค่า agent ที่มี source, channel, sink ได้ด้วยไฟล์ config ไม่ต้องเขียนโปรแกรม มี HDFS sink ให้ใช้ทันที และ event ถูกลบออกจาก channel เมื่อส่งต่อสำเร็จ ส่วน Kafka เป็นระบบกลางที่ผู้ส่งและผู้รับไม่ต้องรู้จักกัน เก็บข้อความไว้ให้ consumer หลายกลุ่มอ่านซ้ำได้ และขยายได้ด้วยการเพิ่ม partition กับ broker ถ้าปลายทางเดียวคือ HDFS ใช้ Flume ง่ายกว่า ถ้าข้อมูลชุดเดียวต้องส่งให้หลายระบบใช้ Kafka เหมาะกว่า และใช้ร่วมกันได้ โดยให้ Kafka รับข้อมูลแล้วให้ Flume เป็น consumer ที่เขียนลง HDFS

## ข้อ 7 (10 คะแนน)

**โจทย์** ตาราง `orders` ใน MySQL มี primary key ชื่อ `order_id` ค่าตั้งแต่ 1 ถึง 1000 ถ้าสั่ง `sqoop import` โดยใช้ `-m 4` จงอธิบายว่า Sqoop แบ่งงานอย่างไร และถ้าตารางไม่มี primary key ต้องทำอย่างไร พร้อมอธิบายบทบาทของ Avro ใน Flume

**แนวคำตอบ**

เมื่อสั่ง sqoop import กับ -m 4 Sqoop รันงาน MapReduce แบบ map-only ที่มี mapper 4 ตัว และแบ่งงานด้วย primary key ขั้นแรก Sqoop query ค่าต่ำสุดและสูงสุดของ order_id ได้ 1 และ 1000 แล้วแบ่งช่วงนี้เป็น 4 ช่วงกว้างเท่ากัน คือประมาณ 1 ถึง 250, 251 ถึง 500, 501 ถึง 750 และ 751 ถึง 1000 mapper แต่ละตัวรัน SELECT เฉพาะแถวในช่วงของตน เช่น where order_id >= 1 and order_id <= 250 แล้วเขียนผลลง HDFS เป็นไฟล์ของตัวเอง ได้ 4 ไฟล์ (part-m-00000 ถึง part-m-00003) การแบ่งนี้แบ่งตามช่วงค่า ไม่ได้แบ่งตามจำนวนแถว ถ้าค่า order_id ไม่สม่ำเสมอ เช่น แถวส่วนใหญ่มี id ระหว่าง 1 ถึง 100 mapper ตัวแรกจะทำงานหนักกว่าตัวอื่นมาก

ถ้าตารางไม่มี primary key Sqoop ไม่รู้ว่าจะแบ่งงานด้วยคอลัมน์ใด ต้องเลือกอย่างใดอย่างหนึ่ง คือระบุคอลัมน์ที่ใช้แบ่งเองด้วย --split-by ชื่อคอลัมน์ (ควรเป็นคอลัมน์ตัวเลขที่ค่ากระจายสม่ำเสมอ) หรือใช้ -m 1 ให้มี mapper ตัวเดียวดึงทั้งตาราง ซึ่งไม่ต้องแบ่งงานแต่ไม่ได้ประโยชน์จากการทำงานขนาน

Avro เป็นรูปแบบข้อมูลแบบ binary ที่กำหนด schema ด้วย JSON และเป็นระบบ RPC ในการเชื่อม agent ของ Flume หลายชั้น Avro sink ของ agent ต้นทางแปลง event เป็น Avro แล้วส่งผ่านเครือข่ายไปยัง Avro source ของ agent ปลายทางที่ hostname และพอร์ตที่ตั้งไว้ ตัวอย่างคือ agent บนเว็บเซิร์ฟเวอร์ใช้ Avro sink ส่งไปที่พอร์ต 4141 ของ agent collector ที่ใช้ Avro source รับ แล้ว collector ใช้ HDFS sink เขียนลง HDFS การใช้ Avro ทำให้ข้อมูลที่ส่งมีขนาดเล็กเพราะเป็น binary และผู้รับอ่านข้อมูลได้ถูกต้องตาม schema

## ข้อ 8 (15 คะแนน)

**โจทย์** โรงพยาบาลแห่งหนึ่งมีข้อมูลการสั่งยาเก็บในฐานข้อมูล MySQL และมีเครื่องวัดสัญญาณชีพของผู้ป่วยส่งค่าทุก 5 วินาที ต้องการทำรายงานยอดใช้ยารายวัน และต้องการแสดงค่าสัญญาณชีพล่าสุดของผู้ป่วยแต่ละคนได้ทันที จงออกแบบ Big Data Pipeline โดยเลือกเครื่องมือในแต่ละขั้นและให้เหตุผล

**แนวคำตอบ**

โจทย์มีข้อมูลสองลักษณะ ข้อมูลการสั่งยาเป็นข้อมูลมีโครงสร้างในฐานข้อมูล MySQL และต้องการรายงานรายวัน จึงประมวลผลแบบ batch ได้ ส่วนสัญญาณชีพเป็นข้อมูลสตรีมที่เข้ามาทุก 5 วินาที (Velocity สูง) และต้องการค่าล่าสุดทันที จึงต้องมีเส้นทางเร็วแยกต่างหาก การออกแบบจึงใช้แนวคิด Lambda Architecture โดยแบ่งตาม 4 ขั้นของ pipeline

ขั้น Ingestion ข้อมูลการสั่งยาใช้ Sqoop ดึงจาก MySQL เข้า Hadoop ทุกคืน เพราะ Sqoop อ่าน schema จากฐานข้อมูลได้เองและดึงแบบขนานด้วย MapReduce ใช้ incremental import ดึงเฉพาะรายการใหม่ตั้งแต่รอบที่แล้ว ไม่ต้องดึงทั้งตารางทุกครั้ง ข้อมูลสัญญาณชีพให้เครื่องวัดส่งข้อความเข้า Kafka topic เดียว ใช้รหัสผู้ป่วยเป็น key เพื่อให้ค่าของผู้ป่วยคนเดียวกันอยู่ partition เดียวกันและเรียงตามเวลา Kafka เหมาะเพราะข้อมูลชุดเดียวต้องส่งไปสองปลายทาง คือที่เก็บถาวรและที่แสดงผลทันที

ขั้น Staging ข้อมูลการสั่งยาเก็บใน HDFS และสร้างเป็นตาราง Hive ที่ partition ด้วยวันที่ เช่น order_date=2026-10-16 เพื่อให้รายงานรายวันอ่านเฉพาะโฟลเดอร์ของวันนั้น ข้อมูลสัญญาณชีพแยกเป็นสองทาง consumer group แรกคือ Flume ที่อ่านจาก Kafka แล้วใช้ HDFS sink เขียนลง HDFS เพื่อเก็บประวัติทั้งหมด consumer group ที่สองเขียนลง HBase โดยใช้ row key เป็นรหัสผู้ป่วยตามด้วยเวลา เช่น P0012-20261016083005 ค่าล่าสุดของผู้ป่วยหนึ่งคนจึงหาได้ด้วย row key ทันที การนำรหัสผู้ป่วยไว้หน้า key ยังทำให้การเขียนกระจายไปหลาย Region และไม่เกิด hotspot แบบที่เกิดเมื่อใช้เวลาอย่างเดียวเป็น key

ขั้น Computation รายงานยอดใช้ยารายวันใช้ Hive query เช่น select drug_code, sum(qty) from drug_orders where order_date='2026-10-16' group by drug_code ซึ่ง Hive แปลงเป็นงาน MapReduce บน YARN ข้อมูลสัญญาณชีพย้อนหลังใน HDFS ใช้ Hive หรือ MapReduce วิเคราะห์แนวโน้มเป็นรอบ ๆ ส่วนการแสดงค่าล่าสุดอ่านจาก HBase ได้โดยตรงเพราะ HBase อ่านรายแถวได้ในเวลาสั้นมาก

ขั้น Workflow Management ใช้ Airflow หรือ Oozie ตั้งเวลาให้งานทำต่อกันทุกคืน คือรัน Sqoop import ก่อน เมื่อสำเร็จจึงรัน Hive สร้างรายงาน ถ้าขั้นใดล้มเหลวให้แจ้งเตือนและรันซ้ำ ส่วนเส้นทาง Kafka ไป HBase ทำงานต่อเนื่องตลอดเวลาไม่ต้องตั้งเวลา

ข้อเสียของการออกแบบนี้คือต้องดูแลสองเส้นทางและตรรกะสองชุดตามลักษณะของ Lambda แต่จำเป็นเพราะโจทย์ต้องการทั้งรายงานที่ถูกต้องจากข้อมูลทั้งวันและค่าที่เห็นได้ทันที
