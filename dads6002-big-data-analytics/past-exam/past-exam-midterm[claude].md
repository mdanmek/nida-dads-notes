## ข้อ 1 (10 คะแนน) หลักการและขั้นตอนของ MapReduce พร้อมตัวอย่างนับจำนวนค่าบวกและค่าลบ

MapReduce เป็น framework สำหรับประมวลผลข้อมูลขนาดใหญ่แบบกระจายบน cluster ผู้ใช้เขียนแค่สองฟังก์ชันคือ map กับ reduce ส่วน framework จัดการเรื่องแบ่งงาน ส่งข้อมูลข้ามเครื่อง และรันงานซ้ำเมื่อเครื่องล้ม หลักการสำคัญคือส่งโปรแกรมไปรันที่เครื่องที่เก็บข้อมูลอยู่ (data locality) แทนการดึงข้อมูลมารวมที่เครื่องเดียว และ task แต่ละตัวทำงานอิสระต่อกันไม่มีตัวแปรร่วม จึงรันซ้ำได้ผลเดิมเมื่อมี task ล้ม

ขั้นตอนการทำงานมีสามช่วง ช่วงแรกคือ map ไฟล์ input ใน HDFS ถูกแบ่งเป็น input split (ปกติเท่ากับหนึ่ง block) แต่ละ split มี map task หนึ่งตัวอ่านทีละบรรทัดแล้วปล่อยผลออกมาเป็นคู่ key กับ value ช่วงที่สองคือ shuffle and sort ระบบนำคู่ key value จากทุก mapper มาจัดกลุ่มตาม key เรียงลำดับ และส่ง key เดียวกันทั้งหมดไปที่ reducer ตัวเดียวกัน (เลือก reducer ด้วย partitioner คือ hash(key) mod จำนวน reducer) ช่วงที่สามคือ reduce reducer ได้รับ key หนึ่งตัวพร้อมรายการ value ทั้งหมดของ key นั้น แล้วรวมผลและเขียนผลลัพธ์ลง HDFS ถ้าต้องการลดข้อมูลที่ส่งข้ามเครือข่าย ใส่ combiner ที่ทำงานเหมือน reducer ย่อยบนเครื่อง mapper ได้ เพราะการบวกเป็นการรวมที่สลับลำดับได้

ตัวอย่างการนับค่าบวก (รวม 0) และค่าลบ ให้ mapper อ่านตัวเลขทีละบรรทัด ถ้าค่า >= 0 ส่ง ("positive", 1) ถ้าค่า < 0 ส่ง ("negative", 1) reducer รับแต่ละ key แล้วบวกค่า 1 ทั้งหมดเข้าด้วยกัน

```
map(line):
    x = int(line)
    if x >= 0: emit('positive', 1)
    else:      emit('negative', 1)

reduce(key, values):
    emit(key, sum(values))
```

ไล่ข้อมูลตัวอย่าง 1, -2, 0, 8, -5 ผลจาก map คือ (positive,1) (negative,1) (positive,1) (positive,1) (negative,1) หลัง shuffle and sort ได้ positive → [1,1,1] และ negative → [1,1] reducer รวมได้ผลลัพธ์ positive 3 และ negative 2

## ข้อ 2 (15 คะแนน) คุณสมบัติ 5V ของ Big Data

Big Data ไม่ได้นิยามด้วยขนาดตายตัว แต่นิยามด้วยลักษณะที่ทำให้เครื่องมือแบบเดิม (ฐานข้อมูลเครื่องเดียว) จัดการไม่ไหว ลักษณะเหล่านี้สรุปเป็น 5V ได้แก่ Volume, Velocity, Variety, Veracity และ Value

Volume คือปริมาณข้อมูลที่มหาศาลและมาจากหลายแหล่ง จนเก็บในเครื่องเดียวไม่ได้ และการอ่านข้อมูลทั้งหมดด้วยเครื่องเดียวใช้เวลานานเกินไป ตัวอย่างเช่นประวัติการเบิกจ่ายยาของโรงพยาบาลทุกสาขาย้อนหลังหลายปีในระดับรายรายการ ปัญหานี้แก้ด้วยการเก็บแบบกระจายเช่น HDFS ที่ตัดไฟล์เป็น block แล้วกระจายไว้หลายเครื่อง

Velocity คือความเร็วที่ข้อมูลเกิดขึ้นและไหลเข้าระบบอย่างต่อเนื่อง บางงานต้องประมวลผลแบบ real-time คือได้ผลภายในไม่กี่วินาทีหลังข้อมูลเกิด การประมวลผลรอบละคืนจึงไม่ทัน ตัวอย่างเช่นสัญญาณจากเซนเซอร์อุณหภูมิตู้เย็นเก็บวัคซีนที่ส่งทุกไม่กี่วินาที หรือ log การคลิกบนเว็บไซต์ เครื่องมือที่ช่วยคือ Flume หรือ Kafka สำหรับรับข้อมูลสตรีม

Variety คือความหลากหลายของแหล่งและชนิดข้อมูล มีทั้งข้อมูลมีโครงสร้าง (ตารางในฐานข้อมูล) ข้อมูลกึ่งมีโครงสร้าง (JSON, XML, log) และข้อมูลไม่มีโครงสร้าง (ข้อความ ภาพ เสียง) schema เดียวรับข้อมูลทุกแบบไม่ได้ ตัวอย่างเช่นตารางใบสั่งซื้อจาก ERP ไฟล์ PDF ใบแจ้งหนี้ และ JSON จากระบบของผู้ขาย ต้องนำมารวมกันเพื่อวิเคราะห์

Veracity คือความน่าเชื่อถือและคุณภาพของข้อมูล ได้แก่ อคติ (bias) สัญญาณรบกวน (noise) ค่าผิดปกติ และข้อมูลขาดหาย ถ้าข้อมูลไม่ถูกต้อง ผลวิเคราะห์ก็นำไปใช้ไม่ได้ ตัวอย่างเช่นยาตัวเดียวกันมีหลายรหัส หรือแต่ละสาขาบันทึกหน่วยนับไม่ตรงกัน ต้องทำความสะอาดข้อมูลก่อนใช้

Value คือคุณค่าทางธุรกิจที่ได้จากข้อมูล ข้อมูลที่เก็บไว้มากแต่ไม่ได้นำไปใช้เป็นเพียงต้นทุน ตัวอย่างเช่นนำข้อมูลการใช้ยาจริงไปพยากรณ์จุดสั่งซื้อ เพื่อลดของขาดและของหมดอายุ

สามตัวแรกคือ Volume, Velocity และ Variety เป็นปัญหาทางเทคนิค และเป็นเหตุผลที่ต้องใช้ระบบกระจายอย่าง Hadoop ส่วน Veracity เป็นเรื่องความถูกต้องของข้อมูล และ Value เป็นเป้าหมายสุดท้ายของการลงทุนในระบบ Big Data ทั้งหมด

## ข้อ 3 (10 คะแนน) การวิเคราะห์ข้อมูลมีกี่แบบ

การวิเคราะห์ข้อมูลแบ่งได้ 4 แบบตามแผนภาพของ Gartner เรียงจากทำง่ายไปทำยาก และคุณค่าที่ได้สูงขึ้นตามลำดับ แต่ละแบบตอบคำถามต่างกัน

แบบที่ 1 Descriptive analytics ตอบคำถามว่าเกิดอะไรขึ้น (What happened?) เป็นการมองย้อนหลัง (hindsight) สรุปข้อมูลในอดีตออกมาเป็นรายงานหรือ dashboard ตัวอย่างเช่น รายงานว่าเดือนที่แล้วสาขาใดใช้ถุงมือทางการแพทย์มากที่สุด

แบบที่ 2 Diagnostic analytics ตอบคำถามว่าทำไมจึงเกิด (Why did it happen?) เป็นการหาสาเหตุ (insight) ด้วยการเจาะลึกและเปรียบเทียบข้อมูล ตัวอย่างเช่น พบว่ายอดใช้ถุงมือเพิ่มขึ้นเพราะจำนวนการผ่าตัดเพิ่มขึ้น หรือเพราะเปลี่ยนไปใช้ยี่ห้อใหม่ที่ขาดง่าย

แบบที่ 3 Predictive analytics ตอบคำถามว่าจะเกิดอะไรขึ้น (What will happen?) เป็นการมองไปข้างหน้า (foresight) โดยใช้แบบจำลองทางสถิติหรือ machine learning ตัวอย่างเช่น พยากรณ์ความต้องการถุงมือในไตรมาสหน้า

แบบที่ 4 Prescriptive analytics ตอบคำถามว่าควรทำอย่างไรให้เกิดผลที่ต้องการ (How can we make it happen?) เป็นการหาทางเลือกที่ดีที่สุด (optimization) ตัวอย่างเช่น แนะนำปริมาณและเวลาสั่งซื้อถุงมือที่ทำให้ต้นทุนรวมต่ำที่สุดโดยของไม่ขาด

สองแบบแรกช่วยให้เข้าใจอดีต ส่วนสองแบบหลังช่วยตัดสินใจเรื่องอนาคต องค์กรมักไล่ทำจากแบบที่ 1 ขึ้นไป เพราะการพยากรณ์และการแนะนำต้องอาศัยข้อมูลอดีตที่สรุปและเข้าใจสาเหตุแล้ว

## ข้อ 4 (10 คะแนน) ขั้นตอนของ Big Data Pipeline และเครื่องมือ

Big Data Pipeline คือลำดับขั้นที่นำข้อมูลดิบจากแหล่งต่าง ๆ มาจนได้ผลวิเคราะห์ที่ใช้งานได้ โดยทำงานอัตโนมัติและวนกลับไปปรับปรุงผลเมื่อมีข้อมูลใหม่ แบ่งได้เป็น 4 ขั้น

ขั้นที่ 1 Ingestion คือการนำข้อมูลจากแหล่งภายนอกเข้าสู่ระบบ ข้อมูลที่อยู่ในฐานข้อมูลเชิงสัมพันธ์ใช้ Sqoop นำเข้าแบบเป็นชุด (batch) ข้อมูลที่ไหลต่อเนื่องเช่น log จากเว็บเซิร์ฟเวอร์ใช้ Flume หรือ Kafka

ขั้นที่ 2 Staging คือการเก็บข้อมูลที่นำเข้ามาไว้ในที่พัก ซึ่งมักเป็น data lake ที่เก็บข้อมูลดิบไว้ก่อนแล้วค่อยกำหนดโครงสร้างตอนอ่าน (schema on read) เครื่องมือได้แก่ HDFS สำหรับไฟล์ขนาดใหญ่ HBase สำหรับข้อมูลที่ต้องอ่านเขียนรายแถวอย่างรวดเร็ว และ Hive สำหรับกำหนดโครงสร้างตารางให้ไฟล์ใน HDFS

ขั้นที่ 3 Computation คือการประมวลผลและวิเคราะห์ข้อมูล เช่น ทำความสะอาด รวมยอด และสร้างแบบจำลอง เครื่องมือได้แก่ MapReduce ที่รันบน YARN, Hive ที่แปลงคำสั่งแบบ SQL เป็นงาน MapReduce และ Spark สำหรับงานที่ต้องการประมวลผลในหน่วยความจำ

ขั้นที่ 4 Workflow Management คือการจัดลำดับและตั้งเวลาให้ขั้นตอนข้างต้นทำงานต่อกันอัตโนมัติ ถ้าขั้นใดล้มเหลวก็แจ้งเตือนหรือรันซ้ำ เครื่องมือได้แก่ Oozie ที่เขียน workflow เป็น XML และ Airflow ที่เขียน DAG ด้วย Python และตั้งเวลาด้วย cron

ตัวอย่างจริงเช่นทุกคืน Airflow สั่ง Sqoop ดึงตารางยอดขายจาก MySQL เข้า HDFS แล้วสั่ง Hive สรุปยอดขายรายสาขา ผลที่ได้นำไปทำรายงาน และใช้ปรับแบบจำลองพยากรณ์ในรอบถัดไป

## ข้อ 5 (15 คะแนน) ส่วนประกอบและหน้าที่ของ HDFS และ YARN

HDFS (Hadoop Distributed File System) เป็นระบบไฟล์แบบกระจายที่ตัดไฟล์เป็น block ขนาด 128 MB แล้วเก็บกระจายไว้หลายเครื่อง แต่ละ block ทำสำเนา 3 ชุดไว้ต่างเครื่องเพื่อให้ทนต่อเครื่องเสีย ไฟล์ทำงานแบบ WORM คือเขียนครั้งเดียวอ่านได้หลายครั้ง แก้กลางไฟล์ไม่ได้ เหมาะกับไฟล์ขนาดใหญ่ HDFS เป็นสถาปัตยกรรมแบบ master/worker มีส่วนประกอบดังนี้

NameNode เป็น master ทำหน้าที่เก็บ metadata ของระบบไฟล์ คือโครงสร้างโฟลเดอร์ ชื่อไฟล์ ไฟล์แต่ละไฟล์ประกอบด้วย block ใดบ้าง และ block แต่ละตัวอยู่ที่ DataNode ใด metadata เก็บอยู่ในหน่วยความจำเพื่อให้ตอบได้เร็ว และบันทึกลงดิสก์เป็นไฟล์ fsimage (ภาพรวมของระบบไฟล์ ณ จุดหนึ่ง) กับ edit log (รายการการเปลี่ยนแปลงหลังจากนั้น) NameNode ไม่ได้รับส่งข้อมูลจริง เมื่อ client จะอ่านไฟล์ client ถาม NameNode ว่า block อยู่ที่ใด แล้วไปอ่านจาก DataNode โดยตรง

DataNode เป็น worker ที่อยู่บนทุกเครื่องใน cluster ทำหน้าที่เก็บ block ของข้อมูลจริงบนดิสก์ อ่านเขียน block ตามคำขอของ client และส่ง heartbeat กับ block report ไปให้ NameNode เป็นระยะ ถ้า NameNode ไม่ได้รับ heartbeat จาก DataNode ใด จะถือว่าเครื่องนั้นเสีย แล้วสั่งทำสำเนา block ที่อยู่บนเครื่องนั้นเพิ่มจากสำเนาที่เหลือ

Secondary NameNode ทำหน้าที่ checkpoint คือนำ fsimage กับ edit log มารวมกันเป็น fsimage ใหม่เป็นระยะ เพื่อไม่ให้ edit log ยาวเกินไปและ NameNode เริ่มต้นใหม่ได้เร็ว Secondary NameNode ไม่ใช่ NameNode สำรองที่ทำงานแทนได้ทันที

YARN (Yet Another Resource Negotiator) เป็นชั้นจัดการทรัพยากรของ cluster แยกการจัดสรรทรัพยากรออกจากการควบคุมแอปพลิเคชัน ทำให้ cluster เดียวรันงานได้หลายแบบ เช่น MapReduce และ Spark มีส่วนประกอบดังนี้

ResourceManager มีหนึ่งตัวต่อ cluster ทำหน้าที่จัดสรรทรัพยากร (CPU และหน่วยความจำ) ให้แอปพลิเคชันทั้งหมด ภายในมี Scheduler ที่ตัดสินว่าแอปใดได้ทรัพยากรเท่าไร และ ApplicationsManager ที่รับ job จาก client และเริ่ม ApplicationMaster ให้แต่ละแอป รวมถึงเริ่มใหม่เมื่อ ApplicationMaster ล้ม

NodeManager อยู่บนทุกเครื่อง worker ทำหน้าที่เปิดและดูแล container (หน่วยทรัพยากรที่ใช้รันงาน) บนเครื่องของตน ติดตามการใช้ทรัพยากร และส่ง heartbeat สถานะเครื่องไปให้ ResourceManager

ApplicationMaster มีหนึ่งตัวต่อหนึ่งแอปพลิเคชัน รันอยู่ใน container แรกของแอป ทำหน้าที่ขอ container จาก ResourceManager สำหรับงานย่อย (เช่น map task และ reduce task) สั่ง NodeManager ให้เปิด container ติดตามความคืบหน้า และสั่งรันงานย่อยใหม่เมื่องานใดล้ม เมื่อแอปเสร็จก็แจ้ง ResourceManager และคืนทรัพยากร

ลำดับการทำงานคือ client ส่ง job ไปที่ ResourceManager จากนั้น ResourceManager สั่ง NodeManager เปิด container สำหรับ ApplicationMaster แล้ว ApplicationMaster ขอ container เพิ่มสำหรับงานย่อย โดยเลือกเครื่องที่อยู่ใกล้ข้อมูลใน HDFS ถ้าทำได้ แล้วจึงสั่งรันงาน

## ข้อ 6 (10 คะแนน) วิธีที่ Hive ทำคำสั่ง

Hive เป็น data warehouse บน Hadoop ที่ให้ใช้ภาษา HQL ซึ่งคล้าย SQL กับไฟล์ใน HDFS เมื่อได้รับคำสั่ง Hive อ่าน schema และตำแหน่งไฟล์ของตารางจาก Metastore (ฐานข้อมูลเชิงสัมพันธ์เช่น MySQL ที่เก็บ metadata) แล้ว compile คำสั่งเป็น execution plan ที่ประกอบด้วยงาน MapReduce และคำสั่ง HDFS

### 6.1 ACID Operations (Insert/Update/Delete)

HDFS แก้ข้อมูลกลางไฟล์ไม่ได้ Hive จึงทำ in-place update ไม่ได้ แต่ยังรองรับ insert, update และ delete แบบ ACID (Atomicity, Consistency, Isolation, Durability) ได้ด้วยวิธีเขียนไฟล์ใหม่แทนการแก้ไฟล์เดิม ตารางต้องประกาศเป็น transactional และเก็บเป็นไฟล์ ORC

ข้อมูลหลักของตารางหรือ partition เก็บอยู่ใน base files เมื่อมีธุรกรรม insert, update หรือ delete Hive ไม่แตะ base แต่เขียนการเปลี่ยนแปลงลงไฟล์เล็กชุดใหม่เรียกว่า delta files ตอนอ่าน Hive อ่านทั้ง base และ delta แล้วนำการแก้ไขและการลบใน delta มาใช้ทับข้อมูลใน base จึงได้ข้อมูลล่าสุด เมื่อ delta สะสมมากขึ้น การอ่านช้าลงเพราะต้องรวมไฟล์จำนวนมาก Metastore server จึงรันงาน MapReduce เบื้องหลังเป็นระยะเพื่อรวม delta เข้ากับ base เป็นไฟล์ชุดใหม่ เรียกว่า compaction แล้วลบไฟล์เก่าเมื่อไม่มีใครอ่านอยู่

ผลของกลไกนี้คือการ update หรือ delete บ่อย ๆ ไม่มีประสิทธิภาพ เพราะทุกครั้งสร้างไฟล์ใหม่และต้องรวมไฟล์ภายหลัง Hive จึงเหมาะกับการเพิ่มข้อมูลเป็นก้อนแล้วอ่านวิเคราะห์

### 6.2 Select with Group by และ Aggregation

ตัวอย่างคำสั่ง `select country, count(*), sum(amount) from sales group by country;` Hive แปลงเป็นงาน MapReduce หนึ่งงาน ใน map phase แต่ละ mapper อ่าน block ของไฟล์ตาราง sales แปลงแต่ละบรรทัดเป็นแถวตาม schema แล้วปล่อยคู่ key value โดยใช้คอลัมน์ใน group by (country) เป็น key และค่าที่ต้องรวม (1 และ amount) เป็น value Hive รวมผลบางส่วนฝั่ง map ไว้ก่อนได้ (เหมือน combiner) เช่นรวมยอดของประเทศเดียวกันใน mapper เดียวกัน เพื่อลดข้อมูลที่ต้องส่งข้ามเครือข่าย

ใน shuffle and sort ระบบส่งแถวที่มี country เดียวกันทั้งหมดไปที่ reducer ตัวเดียวกันและเรียงตาม key ใน reduce phase reducer นำ value ของแต่ละ country มารวม คือนับจำนวนแถวสำหรับ count และบวก amount สำหรับ sum แล้วเขียนผลลัพธ์หนึ่งแถวต่อหนึ่งประเทศลง HDFS เช่น ถ้ามีแถว (TH,100) (US,50) (TH,30) ผลคือ TH 2 130 และ US 1 50

## ข้อ 7 (15 คะแนน) ส่วนประกอบของ HBase และวิธีที่อ่านเขียนได้เร็ว

HBase เป็นฐานข้อมูล NoSQL แบบ column family ที่ทำงานบน HDFS เก็บข้อมูลเป็นแถวที่เข้าถึงด้วย row key และเรียงแถวตาม row key ไว้เสมอ ใช้กับงานที่ต้องอ่านหรือเขียนรายแถวแบบสุ่มด้วยความเร็วสูงบนข้อมูลขนาดใหญ่ ซึ่ง HDFS อย่างเดียวทำไม่ได้ ส่วนประกอบมีดังนี้

Table ถูกแบ่งตามช่วงของ row key เป็น Region แต่ละ Region มี start key และ end key เมื่อ Region โตถึงเกณฑ์จะแบ่ง (split) เป็นสอง Region ทำให้ตารางขยายข้ามหลายเครื่องได้

RegionServer ดูแล Region หลาย Region ทำหน้าที่รับคำสั่งอ่านเขียนของ Region ที่ตนถืออยู่ ภายใน RegionServer มี WAL (Write-Ahead Log) ซึ่งเป็นไฟล์บน HDFS บันทึกการเปลี่ยนแปลงทุกครั้งไว้ใช้กู้คืน มี MemStore ซึ่งเป็นแคชฝั่งเขียนในหน่วยความจำ เก็บข้อมูลใหม่โดยเรียงตาม row key (หนึ่งตัวต่อหนึ่ง column family ต่อหนึ่ง Region) มี BlockCache ซึ่งเป็นแคชฝั่งอ่าน เก็บข้อมูลที่ถูกอ่านบ่อยไว้ในหน่วยความจำ เมื่อเต็มจะไล่ข้อมูลที่ไม่ได้ใช้นานที่สุดออกก่อน (LRU) และมี HFile ซึ่งเป็นไฟล์บน HDFS ที่เก็บคู่ KeyValue เรียงตาม key

HMaster ทำหน้าที่มอบหมาย Region ให้ RegionServer ย้าย Region เพื่อกระจายโหลด เฝ้าดู RegionServer และรับคำสั่งจัดการตาราง เช่น create, alter, drop HMaster ไม่ได้อยู่ในเส้นทางการอ่านเขียนข้อมูลปกติ

ZooKeeper ทำหน้าที่ประสานงานใน cluster รู้ว่าเซิร์ฟเวอร์ใดยังทำงานอยู่จาก heartbeat แจ้ง HMaster เมื่อ RegionServer ล้ม และเก็บตำแหน่งของ META table

META table (hbase:meta) เก็บว่าช่วง row key ใดอยู่ใน Region ใดและ RegionServer ใด client หาข้อมูลโดยถาม ZooKeeper ว่า META table อยู่ที่ไหน ถาม META table ว่า row key ที่ต้องการอยู่ที่ RegionServer ใด แล้วติดต่อ RegionServer นั้นโดยตรง และเก็บตำแหน่งไว้ใช้ครั้งต่อไป

HDFS เป็นที่เก็บถาวรของ WAL และ HFile และทำสำเนาข้อมูลไว้หลายเครื่อง

เหตุที่ HBase เขียนได้เร็ว คือเมื่อ client ส่ง put RegionServer เขียนรายการต่อท้าย WAL ก่อน (การต่อท้ายไฟล์เร็วกว่าการเขียนแบบสุ่ม) แล้วใส่ข้อมูลลง MemStore ในหน่วยความจำ แล้วตอบ client ว่าสำเร็จทันที ไม่ต้องรอเขียนลง HFile เมื่อ MemStore สะสมข้อมูลมากพอ จึง flush ข้อมูลที่เรียงแล้วทั้งก้อนเป็น HFile ใหม่ทีเดียว การเขียนแบบสุ่มหลายครั้งจึงกลายเป็นการเขียนไฟล์ตามลำดับครั้งเดียว ถ้า RegionServer ล้มก่อน flush ก็กู้ข้อมูลคืนได้ด้วยการ replay WAL ที่อยู่บน HDFS

เหตุที่ HBase อ่านได้เร็ว คือ client รู้ตำแหน่ง RegionServer จาก META table และไปหาโดยตรง RegionServer ค้น row key ใน BlockCache และ MemStore ซึ่งอยู่ในหน่วยความจำก่อน ถ้าไม่พบจึงค้นใน HFile ด้วย binary search ซึ่งทำได้เพราะ HFile เรียงตาม key นอกจากนี้ flush แต่ละครั้งเพิ่ม HFile หนึ่งไฟล์ HBase จึงทำ minor compaction อัตโนมัติเพื่อรวม HFile เล็กเป็นไฟล์ใหญ่ และทำ major compaction เมื่อสั่งด้วยคำสั่ง major_compact เพื่อรวม HFile ทั้งหมดและลบข้อมูลที่ถูกลบออกจริง จำนวนไฟล์ที่ต้องค้นจึงน้อยลงและอ่านเร็วขึ้น

## ข้อ 8 (15 คะแนน) วิธีการทำงานและลักษณะข้อมูลที่ Sqoop และ Flume นำเข้าสู่ Hadoop

Sqoop (SQL to Hadoop) เป็นเครื่องมือถ่ายโอนข้อมูลระหว่างฐานข้อมูลเชิงสัมพันธ์ (RDBMS) เช่น MySQL หรือ Oracle กับ Hadoop ทั้งขาเข้า (import) ไปยัง HDFS, Hive หรือ HBase และขาออก (export) กลับไปที่ฐานข้อมูล ข้อมูลที่ Sqoop นำเข้าเป็นข้อมูลมีโครงสร้าง คือแถวของตารางที่ทุกแถวมีคอลัมน์ชุดเดียวกัน และนำเข้าเป็นชุด (batch) ไม่ได้ออกแบบมาสำหรับข้อมูลที่ไหลต่อเนื่อง

วิธีการทำงานของ Sqoop เริ่มจากเชื่อมต่อฐานข้อมูลผ่าน JDBC แล้วอ่าน schema ของตาราง (ชื่อคอลัมน์และชนิดข้อมูล) จากฐานข้อมูลโดยตรง จากนั้นสร้าง Java class สำหรับแทนแถวของตาราง แล้วรันงาน MapReduce แบบ map-only (ไม่มี reduce) เพื่อดึงข้อมูลแบบขนาน Sqoop แบ่งงานด้วย primary key โดยหาค่าต่ำสุดและสูงสุดของคีย์ แล้วแบ่งเป็นช่วงเท่า ๆ กันตามจำนวน mapper (ค่าเริ่มต้น 4 กำหนดได้ด้วย -m) แต่ละ mapper ดึงแถวในช่วงของตนด้วยคำสั่ง SELECT แล้วเขียนลง HDFS เป็นไฟล์ข้อความคั่นด้วยจุลภาคโดยค่าเริ่มต้น ถ้าใช้ --hive-import Sqoop จะสร้างตารางใน Hive และโหลดข้อมูลให้ ถ้าใช้ --hbase-table จะเขียนลง HBase นอกจากนี้ยังทำ incremental import ดึงเฉพาะแถวใหม่ในรอบถัดไปได้ ตัวอย่างคำสั่ง

```
sqoop import --connect jdbc:mysql://localhost/shop --username root -P --table orders --target-dir /user/cloudera/orders -m 4
```

Flume เป็นเครื่องมือรวบรวมและย้ายข้อมูลสตรีมปริมาณมาก โดยเฉพาะ log จากหลายเครื่อง เข้าสู่ HDFS อย่างต่อเนื่องและเชื่อถือได้ ข้อมูลที่ Flume นำเข้าเป็นข้อมูลที่เกิดขึ้นต่อเนื่อง เช่น log ของเว็บเซิร์ฟเวอร์ log การคลิก หรือเหตุการณ์จากเซนเซอร์ มักเป็นข้อมูลกึ่งมีโครงสร้างหรือไม่มีโครงสร้าง เช่น บรรทัด JSON หรือข้อความ log

หน่วยข้อมูลของ Flume เรียกว่า event ประกอบด้วย header และ body (ข้อมูลเป็น byte) Flume ทำงานผ่าน agent ซึ่งเป็นโปรเซส Java มีสามส่วน source รับ event จากภายนอกแล้วใส่ลง channel เช่น exec source ที่รันคำสั่ง tail -F อ่าน log หรือ spooling directory source ที่อ่านไฟล์ใหม่ในโฟลเดอร์ channel เป็นที่พัก event ระหว่าง source กับ sink อาจเป็น memory channel (เร็ว แต่ข้อมูลหายถ้า agent ตาย) หรือ file channel (เก็บบนดิสก์ ทนกว่า) sink อ่าน event ออกจาก channel แล้วส่งไปปลายทาง เช่น HDFS sink หรือ Avro sink ที่ส่งต่อไปยัง agent ถัดไป source หนึ่งตัวส่งได้หลาย channel แต่ sink หนึ่งตัวอ่านได้ channel เดียว

ความน่าเชื่อถือของ Flume มาจากธุรกรรม (transaction) ของ channel event จะถูกลบออกจาก channel ก็ต่อเมื่อถูกเก็บลง channel ของ agent ถัดไปหรือปลายทางสุดท้ายเรียบร้อยแล้ว ถ้าส่งไม่สำเร็จ ธุรกรรมจะ rollback และ event ยังอยู่ใน channel รอส่งใหม่ ในงานจริงมักต่อ agent หลายชั้น เช่น agent บนเว็บเซิร์ฟเวอร์ใช้ Avro sink ส่ง event ไปที่ agent ตัวรวม (collector) ที่ใช้ Avro source รับ แล้วใช้ HDFS sink เขียนลง HDFS

สรุปความต่างคือ Sqoop นำเข้าข้อมูลมีโครงสร้างจากฐานข้อมูลเป็นชุดด้วยงาน MapReduce ส่วน Flume นำเข้าข้อมูลสตรีมที่ไหลต่อเนื่องผ่าน agent ที่ประกอบด้วย source, channel และ sink
